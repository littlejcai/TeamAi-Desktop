## 评估目标

确定首个可用桌面版本的最小范围、验证方式与实施顺序。M0 当前只有自检应用，业务页面需从零搭建。Electron 与 fork 复用仍是已有决策；只有出现明确证据才重开技术选型。

|---|---|---|
| 1. 依赖与接口 | 实际 pin 的 Linux 测试是否全绿？desktop-api 是否覆盖资源读取与同步所需入参/输出/错误？写操作是否仍依赖终端交互？ | 命令/API 对照表、缺口与最小 fork 补丁范围 |

## 建议首个实施切片（评估通过后启动）

M1-101 应用骨架 + 最小 IPC 契约 + 一个真实只读流程：打开应用 → 识别初始化状态 → 已初始化用户看到资源列表和状态；未初始化用户获得明确提示。

此切片验收至少包括：真实 core 数据、空态和错误态、renderer 无 Node 权限、IPC 输入校验、可执行的类型检查与测试、Windows 启动 smoke。采用只读切片是建议，最终范围由上述评估确定。

随后按依赖顺序评估资源搜索/详情、同步预览/执行、初始化、贡献、托盘与设置。同步和贡献涉及本地文件与远端写入，分别定义确认、失败恢复和取消语义，不能只检查按钮存在。

## 启动条件

- 当前 pin 的 Ubuntu Node 20/22 类型检查与全量单测通过；Windows 未通过部分单独记录。
- 首个切片范围、API 缺口、验收和验证平台明确。
- 用户走查延期有明确承接任务。
- 为确定的实施范围创建可跟踪任务后开始开发；不把整份历史计划一次性转为已排期承诺。

不新增业务页面，不升级/同步 core，不发布安装包，不替用户决定签名证书与灰度团队，不把未实现的自动更新写成已就绪。
